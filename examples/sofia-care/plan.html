Overview

Qué construimos

Sofia Care es la siguiente generación del producto de asistencia clínica de Omniloy y se construye desde cero en un monorepo: packages/{contracts,sdk} + apps/{api,transcriber,assistant} + db/ + tests/ + evals/. Nada del código actual se porta: los 5 repos existentes (sofia-sdk-core, sofia-api, sofia-transcriber, sofia-sdk-db, sofia-assistants) son la base conceptual — qué funcionó, qué contratos existen, qué deuda no repetir.

La fuente de requisitos es el backlog Jira SOC (proyecto SofIA Care): 64 Features en orden de prioridad (SOC-1 → SOC-64) + 64 Verifications espejo (SOC-65…128), escritas como requisitos de producto sanitario — cada una con user story, criterios de aceptación cuantitativos (p. ej. «contenido no fundamentado ≤ 1 % sobre muestra gold ≥ 100 resúmenes») y riesgos ISO 14971 asociados.

El producto resultante: un widget embebido en el HIS donde el médico obtiene resúmenes fiables del paciente con origen verificable, edita la nota clínica por lenguaje natural con confirmación explícita, consulta guías clínicas con citación real, y graba la consulta con transcripción diarizada por roles — todo con guardrails clínicos, datos en la UE y trazabilidad de auditoría.

Decisiones de arquitectura
  • - Greenfield real: se crea y monta todo de 0. Sin importación de historia git, sin migración de código. Cuando un diseño actual es bueno (la cadena de providers STT con fallback del transcriber, el patrón de anonimización espejo cliente/servidor, el guard chain de la API), se rediseña sobre esa referencia, citándola.
  • - Un solo asistente con deepagents: los 4 grafos actuales (scribe, extraction, transcription, coding) desaparecen; sus capacidades son subagentes/tools de un único deep agent con configuración por tenant en la BD nueva. Las salvaguardas del backlog (guardrail de entrada, modo diagnóstico OFF, recuperación neutral, anonimización pre-LLM) se construyen en el núcleo, no como parches por grafo.
  • - El SDK conserva el diseño, no el código: mismo look & feel y patrón de integración (React + web-component), pero reconstruido como workspaces reales — y con mejoras explícitas de diseño, empezando por el pop-up de inserción/verificación (SOC-18, SOC-23).
  • - Distribución del SDK sin exponer el fuente: el desarrollo vive en el monorepo (privado); a un repo de distribución separado solo llegan los builds, el changelog, el README y el manifest de dependencias. El PR a ese repo se automatiza en cada build; la publicación es manual (un humano revisa, mergea y publica).
  • - La BD es nueva: el esquema de sofia-sdk-db es referencia funcional (tenancy his→groups→keys, plantillas versionadas, auditoría hash-chained); la plataforma (Supabase vs Postgres gestionado) es un spike [needs decision].
  • - Login de usuario nuevo: además de la API key de tenant, el producto incorpora autenticación de usuario vía JWT o SSO (OIDC) — spike [needs decision].
  • - Cumplimiento como requisito de primera clase: residencia UE (inferencia y voz), retención 7 días con borrado verificable, consentimiento, SBOM por release, sellado de salidas con versión de modelo+prompt, y vigilancia poscomercialización — todo viene del backlog SOC, no es un añadido posterior.
Cómo aterriza este plan en Jira (Feature ← Tareas + Verificación, sin subtareas)

El backlog vive en Jira y sigue la estructura del equipo: cada Feature (SOC-1…64) tendrá tareas técnicas (tipo Tarea) y de Verificación enlazadas como issues independientes (Relates), nunca subtareas.

  • - Las sub-issues de este plan son la cantera de las Tareas técnicas: cada una cita en sus prd_refs las Features SOC que implementa; al crearlas en Jira, cada sub-issue se convierte en una o más Tareas enlazadas a su(s) Feature(s). Una sub-issue transversal (p. ej. E3.4 anonimización) se enlaza a todas las Features a las que da servicio.
  • - Las Verifications ya existen (SOC-65…128, espejo 1:1 de cada Feature): se enlazan a su Feature como tarea de verificación y se ejecutan con la maquinaria de E11 (suites gold-standard y harness de integración). Donde haga falta granularidad extra, se crean tareas de verificación adicionales — siempre enlazadas, no subtareas.
  • - El skill create-jira-work-items del equipo ya implementa este patrón (Feature + Tarea + Verificación con Relates); la creación masiva desde este manifest debe seguirlo.
